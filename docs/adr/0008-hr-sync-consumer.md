# ADR 0008: 教务同步——只读消费教务现有集成接口，本地镜像，人工确认落库

**Status:** Accepted
**Date:** 2026-10-10

## Context

ADR 0004 把教务对接推迟到内测之后。用户决定先只做本系统这一侧：**教务（`../hr-management`）一行不改**，按它现有的集成接口形状写消费端，用本地 mock 开发测试；内测后再在教务那边加一个专属 token 接通。

教务现有对外接口是 `backend/app/api/routes/online_form_integration.py`（`/api/integrations/online-form/v1`），原本给在线表单系统用。逐行读过后，有几处现实直接决定了本侧怎么设计：

1. **详情接口给的字段很窄。**`GET /projects/{student_code}` 只返回：姓名、邮箱、在读状态、提交学期（`academic_term.name`，长格式 `25秋季（26年3月提交）`）、课题（`title`）、是否退出、分配列表。**没有学校、年级、性别、报名学期。**
2. **分配里的 id 不全是真人 id。**真实账号是 `user.id`；英方 SA（无系统账号，来自 `SAInfo`）是 `1_000_000 + sa_info_id`；按 `mentor_name` 字符串兜底的 Mentor 是 `2_000_000 + project.id`，IM 兜底是 `3_000_000 + project.id`——**后两种每个项目一个，不是稳定身份**。另外 TA 在接口里叫 `MENTOR`。
3. **`POST /sync-acknowledgements` 把 consumer 写死成 `"EPQ_ONLINE_FORMS"`。**表结构按 `consumer` 区分、本可支持多消费方，但端点不支持。本侧若调用，会挪动在线表单系统的同步位点。
4. **`GET /project-changes` 每次调用都会在教务库里扫全表、插变更行**（`refresh_change_log`）。读接口带写副作用。

## Decision

**1. 永不调用教务的 ack 端点。位点存本地。**
见 Context 3。增量位点（`through_sequence`）存在本系统 `system_config` 里。教务那边的 ack 表对本侧是不存在的。将来教务加了按 consumer 区分的 ack，再评估要不要接。

**2. 先拉进本地镜像表，再按人派生——而不是每次按人去教务现查。**
教务集成接口没有"按老师查项目"的端点，只有全局变更序列 + 单个项目详情。所以：一个全局消费者按变更序列增量拉取 → 详情写进 `hr_projects` 镜像表（原样存 JSON + 抽出 `student_code` / `data_version`）→ 每个导师的同步预览从镜像里按分配筛自己的项目。教务那边的负载只和"变了多少"成正比，和导师人数无关。

**3. 老师↔导师靠管理员手工关联真实账号 id（`tutors.hr_user_id`），不按姓名自动匹配。**
本系统账号与教务账号独立（ADR 0004 决策 2）。中文同名常见，按名字自动对会把学生派给错的人——而派错意味着把一名学生的数据放进了另一位老师的私有空间。只允许关联 `< 1_000_000` 的真实账号 id；合成 id（见 Context 2）拒绝关联。

**4. 只认 `SA` 和 `MENTOR`（=TA）两种分配，不认 `IM`。**
本系统的用户是带课的 SA / TA。Dashboard 的「我的角色：SA / TA」也是这两种。IM 是学习助理，不是本系统的使用者。

**5. 两位都在用本系统的老师带同一名学生 → 各自一份独立记录。**
例如教务里某学生的中方 SA 和 TA 都是本系统用户。本系统的租户边界就是导师（ADR 0004 决策 1），纪要和私密笔记本来就该互不可见。唯一约束是 `(tutor_id, hr_student_code)`，不是 `hr_student_code`。

**6. 字段归属：教务说了算的覆盖，导师说了算的只填空。**

| 本系统字段 | 来源 | 规则 |
|---|---|---|
| `name` | `student.name` | 教务权威，覆盖（剥掉「（一年期）」标记） |
| `submission_round` | `academic_term.name` | 教务权威，覆盖（归一为 `25秋`） |
| `topic` | `title` | **只填空**——英文课题是导师维护的 |
| `contact` | `student.email` | **只填空** |
| `is_one_year` | 姓名里的「（一年期）」 | **只打标不取消**——标记从姓名里剥掉后，这是它唯一的去处；不转存就等于静默丢掉 |
| 其余全部 | — | 不碰（学校、年级等教务接口里本来就没有） |

"教务已标记退出"只在预览里提示，**不自动删除、不自动归档**——删学生会连带销毁纪要。

**7. 手动触发 + 预览确认，不做后台自动落库。**
导师点「从教务同步」→ 看到逐行 diff（新建 / 更新 / 关联已有 / 退出提示）→ 勾选后应用。复用 Excel 导入那套预览/确认交互。不做后台轮询：Context 4 说明每次拉取都在教务库里写东西，内测期没必要持续给它加负载。

**8. 首次同步要能把存量学生"认领"上。**
现有学生都没有 `hr_student_code`。首次同步时，在本导师被分配的项目里按归一后的姓名找本地学生：唯一命中 → 预览里显示「关联到已有学生 X」；多名同名 → 冲突交人工。关联一旦建立，此后只按 code 匹配。

## Alternatives Considered

**直接调教务的 ack 端点** — 省掉本地位点。否决：见 Context 3，会破坏另一个系统的同步。

**每次同步时按导师现查教务** — 不需要镜像表。否决：教务没有按老师查的端点，只能"拉全部变更 → 逐个查详情 → 再过滤"，每个导师每次同步都要重复一遍。

**按姓名自动关联老师** — 管理员省一步。否决：见决策 3，派错学生是隐私事故。

**一名学生只归一位导师（比如优先 SA）** — 与教务"一个项目"一一对应，简单。否决：另一位老师就看不到自己带的学生了，而两人的纪要本就不该共享。

**后台定时自动同步** — 体验更顺。否决为内测期范围外：见决策 7。机制（全局位点 + 镜像）已经支持，加一个定时器即可。

## Consequences

- 同步能补的字段比 Excel 导入少得多：学校、年级、性别、报名学期教务接口里都没有。这些仍需 Excel 导入或手填。将来若教务愿意扩接口，`_mirror_to_student_fields()` 是唯一改动点。
- **英方 SA（`1_000_000+` 段）其实就是本系统的督导（`supervisors`）。**可以顺着分配把督导也同步过来——本次不做，记在这里。
- 接通真实教务需要教务侧一个改动：认一个本系统专用的 service token。在那之前所有开发和测试都对着 `tests/hr_mock.py`。
